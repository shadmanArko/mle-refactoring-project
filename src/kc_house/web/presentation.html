A home buyer wants a price, not a notebook. The model could not be called by an app.

3 · Idea

Six questions in, an honest price out

A visitor cannot type 19 columns. So the product asks only what anyone knows, and fills in the rest with what is typical for that zip code.

Leakage is prevented by construction

Anything learned from data lives inside the pipeline, so cross-validation and the test set can never influence a training feature. A test proves it.

Tiny, pure functions

One function per cleaning step, each unit tested and none changing its input. The same code serves training, the notebook and the API.

6 · Proof

The refactor reproduces the notebook

19 / 19features equal to the notebook within 1e-9
identicaltrain and test rows (hash match)
0.8447held-out R² vs 0.8443 in the notebook
0.08 sfeatures for 21,596 houses, was minutes

Method: run the notebook's own cells once, freeze the outputs, and make the new code match them. The tiny 0.0004 difference is expected: the water feature is now learned from training rows only, as it should be.

7 · Evidence

The notebook's model was not the best one

Cross-validated R² on training data, same features and folds for every model. The gap (0.06) is several times the fold-to-fold noise, so I shipped gradient boosting and kept the notebook's model as the documented reference.

8 · Honesty

Is the number inflated?

0.880random split (the notebook's way)
0.881same house never on both sides
0.877train on the past, test on the future
The score holds up under stricter splits, and the test set was used once, only to judge the champion.
Known weakness: it pulls estimates toward the middle. Cheap houses are overestimated by about $24k, the top quarter underestimated by about $47k.

9 · Product trade-off

What six questions cost

0.880full model, 19 features
0.840six-question estimator
10.5%typical miss, in percent of price
80.3%of test houses fell inside the shown range

The range multiplies the estimate by 0.78 and 1.22. It was calibrated on out-of-fold training predictions, so no test data shaped it, and it landed on its 80% target.

10 · How it is built

Practices you can check in the repo

Tests done

Over 80 automated tests; about 99% of the source is covered; leakage and parity have their own tests.

Continuous integration done

Lint, format, types and tests on every pull request.

Decisions on record done

Five short architecture decision records, each with a diagram.

Safe by default done

Writes need an API key; inputs are bounded; unknown zip codes get a clear message.

Reproducible done

Locked dependencies; every model records its code version, data hash and settings.

Containers done

The model is trained inside the image build. Non-root, read-only image; tested against a real Postgres, including a database outage.

Observable done

JSON logs with a request id and stack traces; health shows model and database state.

Public AWS URL next

Serverless deployment on AWS Lambda with throttling, then a smoke test of the live link.
